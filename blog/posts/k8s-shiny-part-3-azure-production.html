Going to Production: Azure Kubernetes Service for R Shiny

Part 3 of 3: AKS node pools, container registry, Key Vault secrets, OIDC authentication, Log Analytics monitoring, and zero-downtime deployments.

By the time you reach production, the architecture is already understood. The local rig validated the components. What changes moving to Azure is the infrastructure layer beneath the application stack.

From Local to Cloud

Most of the Kubernetes manifests (the ShinyProxy CR, the Redis StatefulSet, the ingress rules) are identical between local and production. What differs is the set of Azure resources surrounding the cluster.

Azure Kubernetes Service (AKS)

AKS is Azure's managed Kubernetes offering. "Managed" means Microsoft operates the Kubernetes control plane (the API server, etcd, the scheduler) and is responsible for its availability. You are responsible for the node pools (the virtual machines that run your workloads) and everything running inside the cluster.

Node Pool Separation

A production AKS cluster for this use case has two node pools with distinct roles:

graph TD AKS["AKS Cluster"] --> SYS["System Node Pool\nSmaller VMs\n- ingress-nginx\n- cert-manager\n- Redis Sentinel\n- ShinyProxy Operator\n- ShinyProxy instances"] AKS --> USR["User Node Pool\nLarger VMs\n- Shiny app containers\n one per active user"] SYS --> SN1["System Node 1"] SYS --> SN2["System Node 2"] USR --> UN1["User Node 1"] USR --> UN2["User Node 2"] USR --> UN3["User Node N\nautoscale"] style SYS fill:#326ce5,color:#fff style USR fill:#f4811f,color:#fff

Separating node pools means infrastructure is never evicted to make room for a surge in user sessions, and the user pool can be autoscaled independently of the system pool.

Virtual Machine Sizing and maxPods

VM sizing is driven by two constraints: the number of pods a node can schedule (maxPods, set at pool creation time and not changeable without replacing the pool) and the memory each pod consumes.

Each Shiny user session typically uses 500MB–2GB of RAM depending on data size and application complexity. The goal is to choose a VM size where both the memory ceiling and the maxPods ceiling are reached at roughly the same workload. Measure this empirically on the local rig before committing, since changing maxPods in production requires a blue/green pool rotation.

Azure Container Registry (ACR)

ACR is Azure's managed Docker registry. Every Shiny app image lives here before it reaches the cluster.

flowchart LR Dev["Developer\nmerges code"] --> CI["CI Pipeline\nGitHub Actions"] CI --> Build["Build Docker image"] Build --> Push["Push to ACR\nyourregistry.azurecr.io/nas:prod"] Push --> AKS["AKS pulls image\non next user session start"] style CI fill:#2088ff,color:#fff style Push fill:#0078d4,color:#fff style AKS fill:#326ce5,color:#fff

A key detail: the image tag is static (e.g., prod), but the image digest behind that tag changes with every CI push. ShinyProxy is configured with imagePullPolicy: Always, which means it checks for a new image every time it starts a Shiny container. This gives you deploys without a maintenance window:

  • Existing user sessions keep running on the old image
  • New sessions start on the new image
  • No orchestrated deployment step needed
  • No user-visible interruption

The one caveat: existing users don't get the new version until their current session ends and they start a new one. For a bug fix that matters, you may want to let users know to reload.

A second caveat worth knowing at scale: imagePullPolicy: Always means every new session start hits ACR to check the manifest, even if the image hasn't changed. At low session volumes this is negligible. At high churn, with many users starting sessions in a short window, the ACR round-trips add latency to session startup and show up in your ACR egress costs. At that point you'd want to look at image pre-pulling or a more explicit tag strategy.

AKS nodes authenticate to ACR via a role assignment at the Azure RBAC level: the AKS cluster's managed identity gets the AcrPull role on the ACR resource. No credentials to rotate, no secrets to store.

Azure Key Vault (Secrets Management)

Shiny applications need secrets: database passwords, API keys, OIDC client credentials, storage account keys. These must never be committed to source control or baked into Docker images.

flowchart TD Admin["Administrator\nstores secret in Key Vault"] --> KV["Azure Key Vault"] KV --> CSI["Secrets Store CSI Driver\nKubernetes add-on"] CSI --> Pod["Shiny Pod\nreceives secret as\nenvironment variable"] AKS_ID["AKS Pod Identity\nManaged Identity"] -->|"authorized to read"| KV style KV fill:#f4a71d,color:#fff style AKS_ID fill:#0078d4,color:#fff

Key properties of this setup: secrets never appear in Kubernetes manifests or environment files; they are fetched at pod start time. Rotation is straightforward: update the value in Key Vault, and the next pod start picks up the new value. Access is auditable: Key Vault logs every read.

Authentication: OIDC Integration

ShinyProxy integrates with an OpenID Connect (OIDC) identity provider for user authentication. This is what lets you restrict access to specific user groups, maintain session identity, and audit who ran what.

sequenceDiagram participant U as User participant I as ingress-nginx participant SP as ShinyProxy participant IDP as Identity Provider participant P as Shiny Pod U->>I: GET https://app.yourdomain.com I->>SP: Forward request SP->>SP: No session — redirect to login SP->>U: Redirect to Identity Provider U->>IDP: Enter credentials IDP->>IDP: Validate credentials IDP->>SP: Authorization code callback SP->>IDP: Exchange code for ID token IDP->>SP: ID token with user info and groups SP->>SP: Validate token, check authorization SP->>P: Start Shiny container for authorized user SP->>U: Session cookie + proxy to Shiny

A staging slot on the identity provider is used for non-production clusters so authentication flows can be tested without affecting production user credentials or audit logs. ShinyProxy's authorization model allows per-app access control: different user groups can access different apps, and unauthorized users see an access-denied page rather than having a pod started for them.

The most common first-day mistake: the redirect URI registered in the identity provider must exactly match what ShinyProxy sends, protocol, domain, path, trailing slash included. A mismatch produces an error at the IdP that doesn't mention ShinyProxy at all. I've seen this waste hours because the error message points nowhere useful.

Networking

A static public IP is reserved in Azure and tied to your DNS record. If the cluster is ever rebuilt, the same IP reattaches and nothing breaks for users. Traffic flows from DNS through an Azure Load Balancer into ingress-nginx, which terminates TLS and forwards to ShinyProxy. The one configuration detail that matters most for Shiny: every layer must be configured to keep long-lived WebSocket connections open, not close them after a short idle period. Get that wrong and users see phantom disconnects with no obvious error. The Azure Load Balancer's default TCP idle timeout is 4 minutes, well under a typical Shiny session. You need to raise it on both sides: service.beta.kubernetes.io/azure-load-balancer-tcp-idle-timeout on the LoadBalancer Service (value in minutes), and nginx.ingress.kubernetes.io/proxy-read-timeout: "3600" on the ingress. Raising only the nginx side doesn't prevent Azure from dropping the connection underneath it. Neither is mentioned prominently in the AKS getting-started documentation.

Observability

Azure's Container Insights streams every pod's logs and lifecycle events into a Log Analytics Workspace. From there you can query pod restarts, session start/stop events, R-side errors, and authentication failures, and wire alerts to fire when something crosses a threshold. For a Shiny cluster this matters more than for typical web apps because the session lifecycle is stateful: you need to know when a pod was stopped unexpectedly, not just that an HTTP request failed.

The Deployment Flow End to End

Putting it all together, from "developer merges a pull request" to "users see the new version":

flowchart TD PR["Developer merges PR\nto main branch"] --> CI["CI pipeline triggers\nGitHub Actions"] CI --> Build["Build Docker image\nwith R + app code"] Build --> Test["Run automated tests"] Test --> Pass{Tests pass?} Pass -->|No| Fail["Build fails\ndeveloper notified"] Pass -->|Yes| Push["Push image to ACR\nunder static tag"] Push --> Done["CI complete\nNo further action needed"] Done -.->|"Next time a user\nstarts a new session"| Pull["AKS pulls new image\nfrom ACR"] Pull --> NewPod["New Shiny pod starts\nwith updated code"] Note["Existing sessions\ncontinue on old image"] style CI fill:#2088ff,color:#fff style Push fill:#0078d4,color:#fff style NewPod fill:#d4edda,color:#1a1a1a style Fail fill:#f8d7da,color:#1a1a1a style Note fill:#fff3cd,color:#1a1a1a

No manual deployment step. No scheduled maintenance window. No coordinated rollout. The new code simply becomes the image new sessions use, while existing sessions continue undisturbed.

Closing Thoughts

When I started this, the goal was straightforward: make a Shiny application serve more than a handful of users without falling over. What I didn't anticipate was how much of the work would be invisible: the timeout that silently drops sessions, the OIDC redirect URI that produces a useless error, the maxPods value that can't be changed without rebuilding the pool. None of those are in the getting-started guides.

One category of disconnect that drove a lot of this work turned out to be Azure Front Door not having session affinity enabled. Redis handles session state (which user maps to which container) but it doesn't control WebSocket connection routing. Without session affinity at the AFD layer, the WebSocket upgrade request could land on a different ShinyProxy instance than the one handling the active connection, breaking the upgrade handshake regardless of what Redis knows. Months of investigation, a config change to fix.
