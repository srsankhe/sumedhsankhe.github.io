Going to Production: Azure Kubernetes Service for R Shiny

Part 3 of 3 — AKS node pools, container registry, Key Vault secrets, OIDC authentication, Log Analytics monitoring, and zero-downtime deployments.

By the time you reach production, the architecture is already understood. The local rig validated the components. What changes moving to Azure is the infrastructure layer beneath the application stack.

Azure Kubernetes Service (AKS)

AKS is Azure's managed Kubernetes offering. "Managed" means Microsoft operates the Kubernetes control plane — the API server, etcd, the scheduler — and is responsible for its availability. You are responsible for the node pools (the virtual machines that run your workloads) and everything running inside the cluster.

Node Pool Separation

A production AKS cluster for this use case has two node pools with distinct roles:

graph TD
    AKS["AKS Cluster"] --> SYS["System Node Pool\nSmaller VMs\n- ingress-nginx\n- cert-manager\n- Redis Sentinel\n- ShinyProxy Operator\n- ShinyProxy instances"]
    AKS --> USR["User Node Pool\nLarger VMs\n- Shiny app containers\n  one per active user"]

    SYS --> SN1["System Node 1"]
    SYS --> SN2["System Node 2"]
    USR --> UN1["User Node 1"]
    USR --> UN2["User Node 2"]
    USR --> UN3["User Node N\nautoscale"]

    style SYS fill:#326ce5,color:#fff
    style USR fill:#f4811f,color:#fff

Separating node pools means infrastructure is never evicted to make room for a surge in user sessions, and the user pool can be autoscaled independently of the system pool.

Virtual Machine Sizing and maxPods

VM sizing is driven by two constraints: the number of pods a node can schedule (maxPods, set at pool creation time and immutable after creation) and the memory each pod consumes.

Each Shiny user session typically uses 500MB–2GB of RAM depending on data size and application complexity. The goal is to choose a VM size where both the memory ceiling and the maxPods ceiling are reached at roughly the same workload. Measure this empirically on the local rig before committing — changing maxPods in production requires a blue/green pool rotation.

Azure Container Registry (ACR)

ACR is Azure's managed Docker registry. Every Shiny app image lives here before it reaches the cluster.

flowchart LR
    Dev["Developer\nmerges code"] --> CI["CI Pipeline\nGitHub Actions"]
    CI --> Build["Build Docker image"]
    Build --> Push["Push to ACR\nyourregistry.azurecr.io/nas:prod"]
    Push --> AKS["AKS pulls image\non next user session start"]

    style CI fill:#2088ff,color:#fff
    style Push fill:#0078d4,color:#fff
    style AKS fill:#326ce5,color:#fff

A key detail: the image tag is static (e.g., prod), but the image digest behind that tag changes with every CI push. ShinyProxy is configured with imagePullPolicy: Always, which means it checks for a new image every time it starts a Shiny container. This gives you zero-downtime rolling deploys for free:

  • Existing user sessions keep running on the old image
  • New sessions start on the new image
  • No orchestrated deployment step needed
  • No user-visible interruption

AKS nodes authenticate to ACR via a role assignment at the Azure RBAC level — the AKS cluster's managed identity gets the AcrPull role on the ACR resource. No credentials to rotate, no secrets to store.

Azure Key Vault (Secrets Management)

Shiny applications need secrets: database passwords, API keys, OIDC client credentials, storage account keys. These must never be committed to source control or baked into Docker images.

flowchart TD
    Admin["Administrator\nstores secret in Key Vault"] --> KV["Azure Key Vault"]
    KV --> CSI["Secrets Store CSI Driver\nKubernetes add-on"]
    CSI --> Pod["Shiny Pod\nreceives secret as\nenvironment variable"]

    AKS_ID["AKS Pod Identity\nManaged Identity"] -->|"authorized to read"| KV

    style KV fill:#f4a71d,color:#fff
    style AKS_ID fill:#0078d4,color:#fff

Key properties of this setup: secrets never appear in Kubernetes manifests or environment files; they are fetched at pod start time. Rotation is straightforward — update the value in Key Vault, and the next pod start picks up the new value. Access is auditable — Key Vault logs every read.

Authentication: OIDC Integration

ShinyProxy integrates with an OpenID Connect (OIDC) identity provider for user authentication. This is what lets you restrict access to specific user groups, maintain session identity, and audit who ran what.

sequenceDiagram
    participant U as User
    participant I as ingress-nginx
    participant SP as ShinyProxy
    participant IDP as Identity Provider
    participant P as Shiny Pod

    U->>I: GET https://app.yourdomain.com
    I->>SP: Forward request
    SP->>SP: No session — redirect to login
    SP->>U: Redirect to Identity Provider
    U->>IDP: Enter credentials
    IDP->>IDP: Validate credentials
    IDP->>SP: Authorization code callback
    SP->>IDP: Exchange code for ID token
    IDP->>SP: ID token with user info and groups
    SP->>SP: Validate token, check authorization
    SP->>P: Start Shiny container for authorized user
    SP->>U: Session cookie + proxy to Shiny

A staging slot on the identity provider is used for non-production clusters — authentication flows can be tested without affecting production user credentials or audit logs. ShinyProxy's authorization model allows per-app access control: different user groups can access different apps, and unauthorized users see an access-denied page rather than having a pod started for them.

Networking: From Public Internet to Shiny Pod

The networking path from a user's browser to their Shiny container traverses several layers:

    style PIP fill:#0078d4,color:#fff
    style LB fill:#0078d4,color:#fff

A static public IP is reserved in Azure before cluster creation. If the cluster is destroyed and recreated, the same IP can be reattached, preserving the DNS mapping.

WebSocket handling is the critical piece for Shiny. Every layer — the load balancer, ingress-nginx, ShinyProxy — must handle long-lived WebSocket connections without premature termination. The key ingress-nginx annotations:

nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
nginx.ingress.kubernetes.io/proxy-send-timeout: "3600"
nginx.ingress.kubernetes.io/proxy-connect-timeout: "60"

These tell nginx to keep WebSocket connections alive for up to an hour of inactivity. The right value depends on your application's expected session length and any upstream timeout (corporate proxies, CDN layers) that might close connections earlier.

Observability: Knowing What's Happening

A production Kubernetes cluster without observability is a black box. The monitoring setup uses Azure's native tooling:

graph TD
    Cluster["AKS Cluster\nall pods"] --> LAW["Log Analytics Workspace"]

    LAW --> KPI["KubePodInventory\npod state, restarts, scheduling"]
    LAW --> CL["ContainerLogV2\napplication stdout and stderr"]
    LAW --> Alerts["Azure Monitor Alerts"]

    Alerts --> Email["Email notification"]
    Alerts --> Webhook["Webhook action group"]

    style LAW fill:#0078d4,color:#fff
    style Alerts fill:#e74c3c,color:#fff

Container Insights v2 streams pod logs and metrics from the cluster to a Log Analytics Workspace (LAW). Two tables are particularly useful:

  • KubePodInventory: pod state transitions, restart counts, scheduling decisions — where you look to understand pod lifecycle behavior
  • ContainerLogV2: everything Shiny and ShinyProxy write to stdout/stderr — R errors, authentication failures, session lifecycle events

Alerts are configured on specific conditions: ShinyProxy pod restart count above threshold, Shiny pod count exceeding expected baseline, node memory pressure. KQL (Kusto Query Language) is used to query the tables and power the alerts.

The Deployment Flow End to End

Putting it all together — from "developer merges a pull request" to "users see the new version":

    CI --> Build["Build Docker image\nwith R + app code"]
    Build --> Test["Run automated tests"]
    Test --> Pass{Tests pass?}
    Pass -->|No| Fail["Build fails\ndeveloper notified"]
    Pass -->|Yes| Push["Push image to ACR\nunder static tag"]
    Push --> Done["CI complete\nNo further action needed"]

    Done -.->|"Next time a user\nstarts a new session"| Pull["AKS pulls new image\nfrom ACR"]
    Pull --> NewPod["New Shiny pod starts\nwith updated code"]

    Note["Existing sessions\ncontinue on old image"]

No manual deployment step. No scheduled maintenance window. No coordinated rollout. The new code simply becomes the image new sessions use, while existing sessions continue undisturbed.

Infrastructure as Code

All the Azure resources — the AKS cluster, the ACR, the Key Vault, the Log Analytics Workspace, the public IP, the role assignments — are defined in code. This gives you reproducibility, auditability, and disaster recovery.

The Kubernetes manifests (ShinyProxy configuration, Redis StatefulSet, ingress rules) are managed with Kustomize — a tool that lets you define a base configuration and layer environment-specific differences on top without forking the base:

Closing Thoughts

The combination of ShinyProxy, Kubernetes, and Azure takes a technology that was designed for individual R scripts and makes it capable of serving many users reliably, securely, and with proper operational hygiene.

The path is not trivial — node pool sizing, WebSocket timeout tuning, OIDC integration, and Redis cluster management each have real complexity. But each complexity has a manageable solution, and the local rig discipline means most of that complexity is resolved before it touches production.

The result is a Shiny deployment that can be handed off to an operations team — or a well-configured CI/CD pipeline — and trusted to run reliably.
