Running R Shiny at Scale: Why Kubernetes Changes Everything

Part 1 of 3 — The problem with traditional Shiny deployments, and the component stack that solves it.

Kubernetes R Shiny ShinyProxy Docker DevOps

I was the developer of a Shiny application. At some point, keeping the cluster it ran on alive became part of my job too — without much documentation on how any of it was set up, and with the cluster itself not having been actively touched in roughly three years. This is what I learned over the next few months.

The Promise and the Pain of Shiny

R Shiny is one of the fastest ways to turn data analysis into a usable web application. A data scientist can go from a working R script to a shareable, interactive dashboard in an afternoon. That speed is genuinely remarkable.

But the moment an organization falls in love with a Shiny app and wants to share it broadly, a problem appears: Shiny was not designed to serve many concurrent users.

At its core, a Shiny app runs inside a single R process. R is single-threaded. When one user clicks a button, their computation runs — and if two users click at the same time, one waits. This is not a bug in Shiny; it is a consequence of what R is. Shiny makes R accessible on the web, but it does not change R's concurrency model.

What "at scale" actually means

Scale for a Shiny application does not necessarily mean millions of users. It means:

  • More than a handful of concurrent users, each needing their own independent session
  • Isolation between users — one user's crash should not affect anyone else
  • Reproducibility — the app behaves the same for every user, every time
  • Maintainability — updating the app should not require coordinating with everyone currently using it

Traditional solutions involve running multiple Shiny Server instances behind a load balancer, but this is difficult to manage, easy to misconfigure, and wastes resources (each instance is always on, whether users are present or not).

The Container Breakthrough

Before Kubernetes, the key insight was containerization.

A container packages an application together with everything it needs to run: the R version, the exact package versions, the system libraries, the environment variables. The result is a single artifact — a Docker image — that behaves identically whether it runs on a developer's laptop or a server in a data center.

For Shiny, this is transformative:

Before containersAfter containers
"Works on my machine"One image, same behavior everywhere
Manual dependency managementDependencies locked in the image
Upgrade = downtimeBuild new image, swap when ready
Shared R processEach user can get their own container

But containers alone do not solve the orchestration problem: who decides where each container runs, how many run at once, what happens when one crashes, and how users connect to them?

Kubernetes in Plain Language

Kubernetes (often abbreviated K8s) is software for managing containers at scale. Think of it as an air traffic control system — it does not fly the planes, but it knows where every plane is, where it needs to go, and what to do when something goes wrong.

Key Kubernetes concepts, explained without jargon:

TermPlain English
PodThe smallest unit — one running container (or a tightly coupled group)
NodeA virtual machine that runs pods
ClusterA group of nodes managed together
NamespaceA logical partition inside a cluster (like folders in a filesystem)
IngressThe front door — routes external traffic to the right internal service
DeploymentA declaration of what should be running and how many copies

Kubernetes continuously watches the declared state ("I want three copies of this container running") and reconciles it against reality ("right now only two are running — starting a third").

ShinyProxy: The Bridge Between Shiny and Kubernetes

Kubernetes is a general-purpose orchestrator. It does not know anything about R, Shiny, or user sessions. To make Kubernetes useful for Shiny, we need a layer that understands both worlds.

ShinyProxy is that layer. It is an open-source Java application that acts as a smart reverse proxy for Shiny apps. When a user authenticates and requests an app:

  1. ShinyProxy checks if the user already has a running container for that app
  2. If not, it instructs Kubernetes to start one
  3. It proxies the user's WebSocket connection to that specific container
  4. When the user leaves or the session times out, ShinyProxy signals Kubernetes to stop the container

This gives every user a fully isolated Shiny session with zero manual coordination.

What ShinyProxy adds to the picture

  • Authentication: integrates with identity providers (OIDC, OAuth2, LDAP) so only authorized users can launch apps
  • Authorization: different user groups can access different apps
  • Resource limits: each container gets bounded CPU and memory, protecting the cluster from runaway R processes
  • Audit trail: every session start and stop is logged

The ShinyProxy Operator: Managing ShinyProxy Itself

Running ShinyProxy inside Kubernetes introduces a meta-problem: how do you manage ShinyProxy's own lifecycle? How do you update it without dropping active user sessions?

This is solved by the ShinyProxy Operator — a Kubernetes controller that manages ShinyProxy instances. The operator watches a custom configuration resource (the ShinyProxy CR) and handles:

  • Starting and stopping ShinyProxy pods
  • Rolling out configuration changes without interrupting active users
  • Creating the right Kubernetes service accounts, roles, and networking rules
graph LR CR["ShinyProxy\nConfiguration\n(Custom Resource)"] --> OP["ShinyProxy\nOperator"] OP --> SP1["ShinyProxy\nInstance A"] OP --> SP2["ShinyProxy\nInstance B\n(during update)"] SP1 --> Pods["User Session\nContainers"] SP2 --> Pods style OP fill:#326ce5,color:#fff

The operator pattern is a common Kubernetes idiom: instead of manually running commands to update configuration, you declare the desired state in a resource file, and a controller continuously reconciles toward it.

Redis: Keeping State Across ShinyProxy Instances

When you run multiple ShinyProxy instances (for high availability or during updates), they need to share knowledge about which user has which container running. This shared state lives in Redis, an in-memory data store.

The setup uses Redis Sentinel — a mode where multiple Redis instances elect a leader and automatically handle failover if the leader becomes unavailable. This means ShinyProxy's session data survives even if one Redis node goes down.

Why Not Just Use Posit Connect?

A fair question. Posit Connect (formerly RStudio Connect) is a commercial product that also solves the Shiny scaling problem. If budget allows and operational simplicity is the priority, it is a legitimate choice.

The Kubernetes path makes sense when:

  • You need full control over the infrastructure (networking, secrets, compute)
  • You are already running Kubernetes for other services
  • You want multi-cloud portability — no vendor lock-in
  • You have specific compliance requirements around where data lives
  • You want to co-locate the Shiny app with other containerized services

None of these are universal arguments. Kubernetes adds real operational complexity — I'd estimate the stack described in this series takes 1.5–2 engineers to operate properly, which Posit Connect largely avoids. The point is knowing what you're trading and why.
