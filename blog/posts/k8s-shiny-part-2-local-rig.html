Validate Before You Spend: A Local Kubernetes Rig for R Shiny

Part 2 of 3: Build a full local Kubernetes cluster on your laptop to catch configuration problems before they become cloud bills.

Kubernetes R Shiny k3s Colima DevOps

Cloud infrastructure mistakes are expensive in ways that are hard to anticipate. A local test rig catches most configuration mistakes before they cost a dollar.

Series: Part 1: Why Kubernetes? · Part 2: The Local Test Rig (you are here) · Part 3: Azure Production Cluster

The Case for a Local Rig

The wrong virtual machine size, a misconfigured ingress rule, a Redis cluster that behaves differently under real traffic than under test conditions. These are not hypothetical risks. They are common, and fixing them in production means either accepting downtime or scrambling under pressure.

The solution is a local test rig: a full replica of the production stack running entirely on a developer's laptop. Not a mock. Not a simplified version. The same components, the same configuration, the same behaviors, just on a smaller scale.

flowchart LR Dev["Developer\nLaptop"] -->|"validate first"| Rig["Local K8s Rig\nColima + k3s"] Rig -->|"promote when confident"| AKS["Azure AKS\nProduction"] style Rig fill:#e8f4f8,stroke:#43bf91,color:#1a1a1a style AKS fill:#0078d4,color:#fff

A well-built local rig lets you:

  • Validate upgrades (new ShinyProxy version, new ingress-nginx version) without touching production
  • Reproduce and debug issues without real users being affected
  • Develop confidence in configuration changes before they go anywhere near production
  • Move fast: the iteration cycle on a local cluster is seconds, not minutes

The Tools

Colima: A Mac-Friendly VM Runtime

On macOS, containers need a Linux virtual machine to run (containers are a Linux technology). Colima is a lightweight, open-source VM runtime. Configure it with 4 CPUs, 8GB RAM, and 60GB disk. That's enough for ShinyProxy, Redis Sentinel, and a handful of Shiny user containers running simultaneously.

k3s: Lightweight Kubernetes

k3s is a certified Kubernetes distribution stripped to its essentials. It runs the full Kubernetes API but without the cloud provider integrations and heavy storage backends you don't need locally. Colima can launch k3s directly, so spinning up a local Kubernetes cluster is a single command.

The Application Stack

Inside the k3s cluster, the stack mirrors production exactly:

Architecture: What's Running and Why

graph TD Browser["Browser\nlocalhost"] --> Ingress subgraph Colima["Colima VM"] subgraph K3s["k3s Kubernetes Cluster"] subgraph NS_SP["namespace: shinyproxy"] Ingress["ingress-nginx"] --> SP["ShinyProxy\nInstance"] SP --> Redis["Redis Sentinel\n(3 pods)"] SP --> UserPods["Shiny App Pods"] Operator["ShinyProxy\nOperator"] -.->|manages| SP CertMgr["cert-manager"] -.->|TLS certs| Ingress end end end style SP fill:#f4811f,color:#fff style Redis fill:#dc382d,color:#fff style Ingress fill:#43bf91,color:#fff style Operator fill:#326ce5,color:#fff

Three choices here that differ from a typical local setup and are worth explaining:

TLS is still present. The temptation is to skip TLS locally ("it's just a test"). Don't. ShinyProxy uses WebSockets, and WebSocket behavior over plain HTTP differs from HTTPS in subtle ways that matter. cert-manager issues self-signed certificates locally; the browser warns, but the stack is exercised correctly.

Redis Sentinel runs at full complexity. Three replicas, leader election, sentinel coordination. Start with the real thing. You'll need it the moment you test failover behavior.

Node pools are simplified. Production uses separate pools for infrastructure and user workloads. Locally, everything runs on one node. This is fine for validating component interactions, not for validating scheduler placement.

The Upgrade Testing Workflow

The primary use case for a local rig is upgrade validation. This is the workflow:

flowchart TD A["Identify upgrade target\ne.g. ShinyProxy 3.0.2 to 3.2.4"] --> B["Update version in local rig config"] B --> C["Rebuild and redeploy the rig"] C --> D{Did it come up?} D -->|No| E["Debug: operator logs,\npod events, Redis state"] E --> B D -->|Yes| F["Smoke test\nlogin, launch app, use app, logout"] F --> G{Pass?} G -->|No| H["Find regression\ncheck release notes vs old config"] H --> I["Fix config or workaround"] I --> F G -->|Yes| J["Extended test\nsession reattach, timeout, pod lifecycle"] J --> K{All behaviors correct?} K -->|No| L["Document gap, decide: accept or fix"] L --> J K -->|Yes| M["Version validated\nPromote to production plan"] style A fill:#e8f4f8,color:#1a1a1a style M fill:#d4edda,stroke:#28a745,color:#1a1a1a

This workflow caught real issues before they reached production. Upgrading from ShinyProxy 3.0.2 to 3.2.4, the session timeout properties were silently renamed: proxy.test-timeout became proxy.container-wait-timeout and proxy.app-init-timeout became proxy.container-wait-time. Nothing in the changelog called this out prominently. The rig surfaced it as a pod-start failure; production would have surfaced it as users unable to launch apps. Same story with ingress-nginx annotation syntax across major versions. These are not the kinds of things you find in a diff.

Node Resource Planning: The maxPods Problem

One of the less-documented aspects of Kubernetes is that each node has a hard limit on the number of pods it can run, set at node creation time (maxPods). This limit is immutable after creation. It also determines how much memory the Kubernetes node agent pre-reserves, even if far fewer pods are actually running.

graph TD Node["Kubernetes Node\n4 CPU / 16 GB RAM"] Node --> Reserve["Kubelet Memory Reservation\nscales with maxPods setting"] Node --> System["System Overhead\nOS + container runtime"] Node --> Infra["Infrastructure Pods\ningress, cert-manager, Redis..."] Node --> Available["Available for User Pods\nShiny sessions"] Reserve --> Note1["Higher maxPods = more reserved\neven when pods are not running"] style Reserve fill:#fff3cd,color:#1a1a1a style Available fill:#d4edda,color:#1a1a1a style Note1 fill:#f8d7da,stroke:#f5c6cb,color:#1a1a1a

The practical implication: if you set maxPods too high, kubelet pre-reserves memory you'll never use. Too low, and you hit the pod count ceiling before the memory ceiling. The local rig is the right place to measure this empirically. In production, changing maxPods requires a blue/green pool rotation; getting it right locally saves significant disruption later.

Apple Silicon Considerations

If you're developing on a Mac with an Apple M-series chip (arm64), Shiny app images built for production (linux/amd64) won't run natively. The recommended strategy:

flowchart LR A["arm64 node\nApple Silicon"] --> B["Infrastructure pods\ningress, Redis, operator"] A --> C["Shiny app pod\nlinux/amd64"] B --> D["Native arm64 images\nFast, no overhead"] C --> E["Emulated via binfmt_misc\nSlower startup, correct behavior"] style D fill:#d4edda,color:#1a1a1a style E fill:#fff3cd,color:#1a1a1a

Build infrastructure images natively for arm64. They run fast. For the Shiny app pod, use the same linux/amd64 image as production, relying on Linux's binfmt_misc for emulation. It's slower to start (20–30 seconds vs 5 seconds for native), but you're testing the actual production image. The tradeoff is worth it.

Testing Session Behavior

Beyond "did it start," the local rig enables systematic testing of session behaviors that are otherwise hard to observe without affecting real users.

sequenceDiagram participant H as Test Harness participant SP as ShinyProxy participant R as Redis participant P as Shiny Pod H->>SP: Open session (user A) SP->>R: Register user session to pod ID SP->>P: Start Shiny container P-->>SP: Ready SP-->>H: Session active Note over H,P: Simulate network interruption H->>H: Drop WebSocket connection H->>SP: Reconnect attempt SP->>R: Look up user session SP-->>H: Reconnected to same container

Running this kind of test systematically, with a Playwright-based harness driving different close scenarios, gives you quantitative answers (how long does reconnect take? how many sessions survive a rolling restart?) before the question comes up in production.

The Rig as a Debugging Environment

When unexpected behavior appears in production, the rig lets you reproduce it without risk. The debugging loop:

flowchart LR Prod["Production observation\nPod keeps restarting"] --> Hypo["Form hypothesis\nRedis connection timeout?"] Hypo --> Repro["Reproduce on rig\nsimulate Redis leader failure"] Repro --> Confirm{Reproduced?} Confirm -->|Yes| Fix["Implement fix\non rig"] Confirm -->|No| Hypo Fix --> Validate["Validate fix\non rig"] Validate --> Promote["Apply fix\nto production"] style Prod fill:#f8d7da,color:#1a1a1a style Fix fill:#d4edda,color:#1a1a1a style Promote fill:#0078d4,color:#fff

What the Local Rig Cannot Tell You

Performance at scale: A laptop cluster cannot tell you how 50 concurrent Shiny sessions will perform. It can tell you that sessions work correctly; it cannot tell you about latency under load.

Network topology: The local rig uses NodePort and localhost DNS. Production uses Azure Load Balancer and public DNS. Networking behaviors, particularly around idle connection timeouts and long-lived WebSockets, can differ.

Managed Kubernetes behaviors: AKS manages the control plane and applies node configurations differently than k3s does. The rig validates application-layer behavior; it doesn't validate AKS-specific behaviors.

The right mental model: the local rig eliminates the configuration and component-interaction bugs that would otherwise surface in production. It reduces the number of things you need to discover there; it doesn't eliminate production testing entirely.
